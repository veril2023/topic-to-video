# R8 · 技能维护指南（怎么改对，而不是改坏）

> 这份文件既是**给人看的操作手册**，也是**给模型的行为约束**。
> 一句话结论：**模型改坏技能，几乎都不是"不会写"，而是"改完没回头查"。**

---

## 1. 技能被写坏的四种方式（全部真实发生过）

| # | 失败模式 | 典型表现 | 根因 |
|---|---|---|---|
| 1 | **口径漂移** | 一处写"片头 1.5s"，另一处写"1.0s"；一处写"单行 ≤19 字"，另一处写"单条 ≤22 字" | 局部修改后**没做全局搜索**，旧值留在别处 |
| 2 | **幻觉引用** | 引用一个不存在的脚本路径 / 不存在的案例编号 | 写路径时凭记忆，没 `ls` 验证 |
| 3 | **过度膨胀** | 入口文件涨到几十 KB，每次开工要读完才能动手，反而降低执行质量 | 什么都往入口塞，不分层 |
| 4 | **留旧不删** | 已作废的门、已删的音效、已换的规格，旧表述在文件里留了很久 | 改新的不标旧的，下游不知道信哪个 |

## 2. 提要求的标准模板（直接复制）

```
【改技能】vertical-explainer-video

目标：<一句话说清要解决什么问题>

改哪一节：<章节号，如 R2 §4.5>
现状：<现在是什么样，为什么不行>
改成：<具体要变成什么，能给数值就给数值>
依据：<用户原话 / 实测数据 / 上一集的教训>
验收标准：<改完怎么判断对了，最好是可执行的检查>
不要动：<明确划出不能碰的范围>
```

**反例（最容易写歪的提法）**：

- ❌「优化一下这个技能」——没有靶子，模型会自作主张重构
- ❌「把字幕改短一点」——"短一点"是多少？必须给数值
- ❌「参考一下上一集」——参考哪一点？钩子结构还是画面风格？

**正例**：

- ✅「把字幕单条上限改成 22 字、停留 ≤4.5s，因为有 15 条超 4.5s，观众读完就划走。
  验收：`qc28_subpacing.py` 跑一遍不报 B2」

## 3. 四条硬要求（每次让模型改技能，都附上）

这四句话能挡掉 80% 的翻车：

1. **「先完整读一遍 SKILL.md 再动手，不要凭记忆改」**
   → 防止模型基于旧版本改，产生"改了等于没改"或"覆盖别人的修改"。

2. **「改完做一次全局一致性搜索，把旧值列出来」**
   → 例如"把 1.5s 改 1.0s"后，必须搜 `1\.5s`、`intro`、`幕0`，确认没有残留。

3. **「把你改的每一处列出来，逐条给我看（章节 + 原文 → 新文）」**
   → 有清单才能验收。不给清单的修改一律视为没改。

4. **「有没有因为这次修改而失效的旧表述？一并处理或标注作废」**
   → 这是"口径漂移"的唯一解药。

## 4. 改完之后的自检清单（8 项，逐条回答）

- [ ] **数值冲突**：新增的数值和全局常量（语速 / 画幅 / 安全区 / 字号 / 时长）有没有矛盾？
- [ ] **旧口径处理**：被取代的旧表述是「删掉」还是「标注作废」？（**不能留着不处理**）
- [ ] **引用有效性**：新写的每个文件路径 / 脚本名，是否真的存在？（`ls` 过）
- [ ] **命令可跑**：新写的示例命令，语法对不对？有没有硬编码某台机器的路径？
- [ ] **长度预算**：`SKILL.md` 是否仍 ≤ 20KB？超了就该往 `references/` 挪。
- [ ] **description 同步**：front matter 的 description 有没有跟着新能力更新？（这是唯一的触发索引）
- [ ] **经验沉淀**：这次踩的坑要不要进 `R6`？
- [ ] **日期与版本**：变更摘要里的日期、版本号是否更新？

## 5. 模型不会自动更新技能

**不会。** 这一条必须说清楚：

- 技能是磁盘上的**普通文件**。只在显式调用写文件操作时才会变。
- 模型不会因为"这次发现了新经验"就自动写进去。默认行为是：做完就结束。
- 想让它沉淀，必须**明确说**：「把这条写进 `R6` 经验库」。

**三个适合沉淀的时机**：

1. 一集交付后（把本集的新教训写进 `R6`）
2. 用户提了新规范（写进对应 reference + 变更摘要）
3. 发现技能自身有错（就地修正 + 在经验库记一条"为什么错"）

**建议句式**：

> 「把这次的三条教训写进 R6；同时检查 SKILL.md 的红线表要不要更新。」

## 6. 多会话并行改技能的冲突风险

如果技能放在所有会话共享的位置，就存在覆盖风险：

| 场景 | 会发生什么 |
|---|---|
| 会话 A 改 R2，会话 B 改 R6 | 通常没问题（不同文件） |
| 会话 A、B 同时改 `SKILL.md` | **后写的覆盖先写的**，且不会报错——最危险的一种 |
| 会话 B 基于旧版 `SKILL.md` 工作 | 它会把会话 A 的修改覆盖掉 |

**三条规避纪律**：

1. **同一时间只让一个会话改技能**。要并行做，就让别的会话只读不写。
2. 改之前先看文件修改时间，确认没有别的会话刚动过。
3. 大改动前先备份：`cp SKILL.md SKILL.md.bak-$(date +%Y%m%d-%H%M%S)`。

## 7. 技能的边界：方法跨项目，内容不跨

| 东西 | 装在哪 | 换个项目还能用吗 |
|---|---|---|
| 技能本身（方法、判据、脚本、模板） | 技能目录（**全局**） | ✅ 能 |
| 内容资产（成片、台账、选题库、帧序列） | 项目目录（**项目级**） | ❌ 不能 |
| 该项目的工作记忆 | `<项目>/.workbuddy/memory/` | ❌ 不跨项目 |

**由此产生一个真实风险**：技能文档里如果写了具体项目路径，
在另一个项目里触发时，它会指向错误的目录。

**正确做法**：在另一个项目里使用时，第一条指令就说清楚：

> 「技能里的项目根路径按**本次工作目录**解释，台账和选题库请从本次目录找；
> 找不到就告诉我，不要猜。」

### 7.1 想改"结构"时，加结构文件，不要改方法论

这是最容易走偏的一类修改。**题材变了 → 想改幕的顺序 → 顺手改了 R1 的幕表**，结果原来能做的题材全坏了。

| 你想要 | 正确动作 | 错误动作 |
|---|---|---|
| 讲崩解类题材 | 复制 `structures/_template.md` → 填槽 → 在 `structures/README.md` §6 登记 | 改 `seven-act.md` 的幕表 |
| 让落点幕换个性质 | 新结构里改 `落点幕` 字段 | 删掉 R1 §6 的钩子范式 |
| 觉得幕太多 | 新结构减到 5 幕，总时长重算 | 从模板里删行，不改 `epcheck` 的时长判据 |

**唯一不可变的是 `structures/README.md` §4 那 8 条**。任何结构只要不满足这 8 条，
就不是"另一种结构"，而是**一条会掉完播率的流水线**——它可能拍出来很好看，但留不住人。

> 加完结构必须做的一件事：**用新结构真的做一集**，做完再回来改它的 `适合 / 不适合`。
> 只推演不加验证的结构，等于给后来用它的人埋坑。

---

## 8. 一句话总纲

> **技能不是记忆，是契约。** 它不会自己长大，也不会自己纠错。
> 你要给它三样东西：**明确的靶子**（改哪一节）、**可验收的标准**（怎么判断对了）、
> **改完的复查**（旧口径有没有残留）。
