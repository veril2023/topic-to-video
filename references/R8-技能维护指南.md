# R8 · 技能维护指南（怎么让模型改对 skill，而不是改坏）

> 这份文件是**给用户看的操作手册**，也是给模型看的行为约束。
> 起因：2026-10-19 一天之内，本技能出现过 9 处口径冲突（详见 §1），全部是"改了局部、忘了全局"造成的。

---

## 1. skill 被写坏的四种典型方式（本技能全部真实发生过）

| # | 失败模式 | 本技能的真实案例 | 根因 |
|---|---|---|---|
| 1 | **口径漂移** | §2 写"深黑 `#07080C` 全季统一"，§4.6 写"v5 深色渐变"；幕0 写 1.5s，片头版式写 1.0s；字幕"单行 ≤19 字"与"单条 ≤22 字"并存 | 局部修改后**没做全局搜索**，旧值留在别处 |
| 2 | **幻觉引用** | 引用 `_audit/epcheck.py`，但脚本实际在项目根而非技能包；引用 `outputs/总策划案` 但没验证文件是否存在 | 写路径时凭记忆，没 `ls` 验证 |
| 3 | **过度膨胀** | SKILL.md 涨到 70.8KB，每次开工要读完才能动手，反而降低执行质量 | 什么内容都往里加，不分层 |
| 4 | **留旧不删** | QC-25c 已作废、片尾 whoosh 已删、9:16 双封面已换 3:4 单封面——旧表述在文件里留了很久 | 改新的不标旧的，下游不知道信哪个 |

**一句话总结：模型写坏 skill，几乎都不是"不会写"，而是"改完没回头查"。**

## 2. 提要求的标准模板（直接复制）

```
【改 skill】math-essence-video

目标：<一句话说清要解决什么问题>

改哪一节：<章节号，如 §4.6 片头版式 / R2 的 4.5>
现状：<现在是什么样，为什么不行>
改成：<具体要变成什么，能给数值就给数值>
依据：<用户原话 / 实测数据 / 上一集的教训>
验收标准：<改完怎么判断对了，最好是可执行的检查>
不要动：<明确划出不能碰的范围>
```

**反例（模型最容易写歪的提法）**：
- ❌「优化一下这个 skill」——没有靶子，模型会自作主张重构
- ❌「把字幕改短一点」——"短一点"是多少？必须给数值
- ❌「参考一下 ep03」——参考哪一点？钩子结构还是画面风格？

**正例**：
- ✅「把字幕单条上限改成 22 字、停留 ≤4.5s，因为 ep05 有 15 条超 4.5s，观众读完就划走。验收：qc28_subpacing.py 跑 ep05 要不报 B2」

## 3. 四条硬要求（每次让模型改 skill，都要附上）

这四句话能挡掉 80% 的翻车：

1. **「先完整读一遍 SKILL.md 再动手，不要凭记忆改」**
   → 防止模型基于旧版本改，产生"改了等于没改"或"覆盖别人的修改"。

2. **「改完做一次全局一致性搜索，把旧值列出来」**
   → 例如"把 1.5s 改 1.0s"后，必须搜 `1\.5s`、`intro`、`幕0`，确认没有残留。

3. **「把你改的每一处列出来，逐条给我看（章节 + 原文 → 新文）」**
   → 有清单才能验收。不给清单的修改一律视为没改。

4. **「有没有因为这次修改而失效的旧表述？一并处理或标注作废」**
   → 这是"口径漂移"的唯一解药。

## 4. 更新后的自检清单（8 项，模型必须逐条回答）

- [ ] **数值冲突**：新增的数值和全局常量表（语速 / 画幅 / 安全区 / 字号 / 时长）有没有矛盾？
- [ ] **旧口径处理**：被取代的旧表述是「删掉」还是「标注作废」？（**不能留着不处理**）
- [ ] **引用有效性**：新写的每个文件路径 / 脚本名，是否真的存在？（`ls` 过）
- [ ] **命令可跑**：新写的示例命令，语法对不对？有没有硬编码别的机器的路径？
- [ ] **长度预算**：SKILL.md 是否仍 ≤ 20KB？超了就该往 references 挪。
- [ ] **description 同步**：front matter 的 description 有没有跟着新能力更新？（这是唯一的触发索引）
- [ ] **经验沉淀**：这次踩的坑要不要进 R6？（编号从 M-85 起）
- [ ] **日期与版本**：变更摘要里的日期、版本号是否更新？

## 5. 模型会不会自动更新 skill？

**不会。** 这一条必须说清楚：

- skill 是磁盘上的**普通文件**。它只在你（或模型）**显式**调用写文件操作时才会变。
- 模型不会因为"这次做的时候发现了新经验"就自动写进去。默认行为是：做完就结束。
- 想让它沉淀，必须**明确说**：「把这条写进 skill 的 R6 经验库，编号 M-85」。

**三种可以说"沉淀"的时机**：
1. 一集交付后（把本集的新教训写进 R6）
2. 用户提了新规范（写进对应 reference + 变更摘要）
3. 发现 skill 自身有错（就地修正 + 在经验库记一条"为什么错"）

**建议的固定句式**：
> 「把这次的三条教训写进 R6，编号从 M-85 起；同时检查 SKILL.md 的 v6 摘要要不要更新。」

## 6. 多会话并行改 skill 的冲突风险

**真实风险**：skill 是用户级（`~/.workbuddy/skills/`），**所有空间、所有会话共用一份**。

| 场景 | 会发生什么 |
|---|---|
| 会话 A 改 R2，会话 B 改 R6 | 通常没问题（不同文件） |
| 会话 A、B 同时改 SKILL.md | **后写的覆盖先写的**，且不会报错——最危险的一种 |
| 会话 B 基于旧版 SKILL.md 工作 | 它会把会话 A 的修改覆盖掉 |

**三条规避纪律**：

1. **同一时间只让一个会话改 skill**。要并行做，就让别的会话只读不写。
2. 改之前先 `ls -la` 看文件修改时间，确认没有别的会话刚动过。
3. 大改动前先备份：`cp SKILL.md SKILL.md.bak-$(date +%Y%m%d-%H%M%S)`——本技能已保留三份历史备份，就是为了能回滚。

## 7. skill 的边界：它跨空间，但内容资产不跨

这是最容易误解的一点：

| 东西 | 装在哪 | 换空间还能用吗 |
|---|---|---|
| skill 本身（方法、判据、脚本、模板） | `~/.workbuddy/skills/math-essence-video/`（**用户级**） | ✅ 能，所有空间共享 |
| 内容资产（成片、SERIES.md、策划案、帧序列） | `<空间目录>/`（**项目级**） | ❌ 不能，只在那个空间里 |
| 该项目的工作记忆 | `<空间>/.workbuddy/memory/` | ❌ 不跨空间 |

**由此产生一个真实风险**：本技能的 SKILL.md 里写了具体路径（`E:/AI Storage/workbuddy/数学系列视频/`）。如果在**另一个空间**里触发这个技能做别的系列，它会指向错误的目录。

**正确做法**：换空间使用时，第一条指令就要说清楚：
> 「技能里的项目根路径指的是 E:/AI Storage/workbuddy/数学系列视频。**本次工作目录是 XXX**，所有相对路径按本次目录解释，SERIES.md 和策划案请从本次目录找；找不到就告诉我，不要猜。」

---

## 8. 一句话总纲

> **skill 不是记忆，是契约。** 它不会自己长大，也不会自己纠错。
> 你要给它三样东西：**明确的靶子**（改哪一节）、**可验收的标准**（怎么判断对了）、**改完的复查**（旧口径有没有残留）。
